# Hubwright: notes for agents

An open-source app to plan, build, secure and run a SharePoint intranet (stages: Connect, Assess, Plan, Build, Secure, Run). Read `docs/architecture.md` and `docs/principles.md` first.

## Commands
- `dotnet build Hubwright.slnx` · `dotnet test tests/Hubwright.Tests`. Warnings are errors; analyzers are at latest-recommended.
- `dotnet build src/Hubwright.Desktop -r win-x64` builds the desktop app (Windows only). `./run.ps1 -Preview` runs it on sample data in `~/.hubwright-preview`.
- Smoke-test the desktop with stderr redirected and `--page <tag>`, in both the real home and `~/.hubwright-preview`. A crashed WinUI app stays alive while Windows Error Reporting dumps it, so "still running" is not proof: read stderr (.NET prints "Stack overflow" and the frames there) and check the Application event log.
- `hubwright skills validate` must pass, and CI runs it. `hubwright skills refresh` checks every quote against the live sources.
- Set `HUBWRIGHT_HOME` to a scratch folder when trying commands, so the real `~/.hubwright` stays clean.

## Rules
- **Open source, no outside branding.** No company or other-project names in code, namespaces or docs. The namespace is `Hubwright`. Never reference sibling repositories; copy and adapt.
- **Reads and writes are separate.** Scans, assessments and proposals only read: `TenantHttp` sends GET, plus the allow-listed read-only theme-manager POST, and sign-in asks only for read scopes (`AccessProfile.ReadOnly`). One app holds both read and write permissions; write scopes are requested only by the Build flow (`AccessProfile.Implement`). `register-app.ps1` creates a read-only app; write permissions need `-Write`.
- **Writes happen in one place.** Only `TenantWriter` writes, only to its allow-list of documented endpoints (site creation, hub register/associate/rename, tenant themes, Graph sharepointSettings limited to `SecurityBaseline.GraphProperties`), and only from a Build or Secure run the person selected and confirmed (typing the tenant name). Never add a DELETE, an archive or an unregister call: those stay guided steps. A new automatic operation needs its Microsoft Learn page in `ImplementationPlanner` (`Source`), an allow-list entry, a read-first "already in place" check, and a test against `FakeSharePoint`.
- **PnP PowerShell is the second write path**, at the user's request, for what SharePoint's REST API doesn't document: home site, navigation, Microsoft's built-in templates (`Invoke-PnPSiteDesign -Template`), look book packages, site header and logo. Also organization news sites, draft welcome posts and designed home pages (`Proposed-home`, drafted; published and made the home page only by the `PublishDesignPage` step, which exists only when the person chose Publish for that site and confirmed it, and which records the previous home page) and the baseline's `Set-PnPTenant` parameters (`PnpScripts.TenantParameters`, checked again by `PnpShell.CheckTenantParameters`). Scripts come only from `PnpScripts` (cmdlet list `PnpScripts.Cmdlets`, none deletes; `PnpShell.CheckCmdlets`); every value goes through `PnpScripts.Q`, `Identifier` or `Literal`; the token travels in `$env:HUBWRIGHT_TOKEN`, never in a script, argument or log; `PnpShell` refuses any other cmdlet. A new PnP step needs its pnp.github.io page as `Source`, by-hand `Instructions`, and a test.
- **Anything without either is a guided step** (app bar global navigation switch, Microsoft 365 org theme, labels, policies, owners): the page opens in the in-app browser with the exact values. Never call an undocumented endpoint to save a click.
- **Rules decide, the AI explains.** Counts, scores and findings come from `Hubwright.Core`. Tools give them to agents. A model never computes a number the core can.
- **Every documented rule is cited.** `basis: documented` needs `source`, an exact `quote` and `reviewed`. Never write a SharePoint limit from memory: fetch the Microsoft Learn page and quote it. Judgment calls are `basis: heuristic`, with a parameter.
- **Unknown is not pass.** A collector that can't read something adds a `ScanIssue` (`ScanAreas`). The facts over it return null, so the rules are "not assessed". Never default a missing value to a passing one.
- **Core is pure.** No I/O, HTTP or model calls in `Hubwright.Core`. The clock for rules is `Values.Now`.
- **Skills are data.** The rule language (`Rules/Expression.cs`) is parsed, never compiled or executed. A new fact goes in `FactCatalog` with a description, and gets a test.
- **Built-in skills are never edited by the app.** Refreshes file proposals; accepting one forks the skill into the user layer.
- **Agents only read or propose.** The tools in `Agents/ToolCatalog.cs` read the workspace; `propose_blueprint` files a proposal. CLI backends get the same tools over `hubwright mcp`, and their built-in tools stay off.
- **Secrets never go in hubwright.json.** Use environment variables or `SecretStore`.
- **The journey drives the app.** Connect → Assess → Plan → Build → Secure → Run is `IntranetJourney` (Core, pure) fed by `Engine/JourneyStatus`; Home and `hubwright status` show it. Navigation is grouped by stage. A stage's `Page` must be a real page tag and its `Command` a real CLI command (test: `Every_stage_points_at_a_desktop_page_and_a_cli_command`). Audit event names (`implement.*`) stay as they are: History parses existing logs.
- **CLI and desktop stay in step.** Every CLI command has a desktop page (see the table in docs/getting-started.md). Put shared logic in Engine (for example `TenantSignIn`), not in `Program.cs` or a page.
- **The security baseline is data** in `skills/security-baseline/baseline.yaml`: per profile target, how it is applied (graph, pnp, guided), the snapshot fact it is read from, and a citation (`basis: heuristic` needs a `note`). `SecurityBaseline` (Core) compares and plans; every automatic baseline step reads first, records `previous` for Restore, and never loosens a stricter value.
- **Run checks only read.** Drift counts a difference as drift only when its build or baseline step finished; unread is "not read", never in place. Scheduled scans run `scan --no-prompt` and never prompt.
- **Microsoft pages move.** `skills refresh --strict` runs weekly in CI (`sources.yml`); when a quote is gone, re-fetch the page and re-quote it, or change the rule to heuristic if Microsoft no longer says it.
- **Proposals** are `IntranetProposalGenerator` (Core, deterministic) driven by `Engine/IntranetProposals`. Every placement, count and template choice comes from code; the AI only writes `Narrative`. The seed's guesses (functions, places, brand) are shown to the user as observations, never silently applied.
- **Every suggestion and step explains itself.** Proposal items and implementation steps carry a `Hint` id from `hints.yaml`; a new step or roadmap line needs a hint (test: `Every_step_and_every_structural_suggestion_has_an_explanation`). A hint's "why" cites rules; it never states a Microsoft limit of its own without `source` and `quote`.
- **Site designs are data** in `skills/site-design/patterns.yaml` (heuristic, each with a `note` and `practices`). `SiteDesigner` (Core, deterministic) gives every site in a proposal a design; an agent's `propose_site_design` is checked by `SiteDesigner.Validate` and waits in AI suggestions; accepting goes through `Engine/SiteDesigns`. Existing sites never get a template applied: the Build drafts a page and the owner publishes it, or Site designs → Publish (`hubwright design apply --publish`) does, after a confirmation that says who notices and asks for the tenant name; cancelling puts the design back (`SiteDesigns.Restore`).
- **Awareness is code-backed.** `Engine/Awareness` (Home's scope card, `hubwright scope`) builds its permission and operation lists from `TenantAuth`, `TenantWriter.Operations` and `PnpScripts.Cmdlets`; a new write path updates it (test: `The_scope_explanation_lists_what_the_code_allows`). Raise `Awareness.Version` when people should read it again.
- **Templates are data** in `skills/site-templates/templates.yaml`, each with Microsoft's page, a verbatim quote and a reviewed date. Never add a template, id or description from memory. Sketch `sections` are Hubwright's wireframes and must be labelled as such wherever they are shown.
- **Sign-in** is `TenantSignIn.RunAsync`: Graph first (browser by default, Windows broker or device code), then the tenant prefix from `GET /v1.0/sites/root`, then SharePoint consent. Never ask for a tenant name the user can't know.
- **Theme and icons:** Settings → Appearance (or the switch in the navigation) sets `desktop.theme` (System, Light, Dark), applied live by `MainWindow.ApplyTheme`. Brushes come only from `Ui.Resource` (it reads the window's actual theme after a live switch); every `ContentDialog` sets `RequestedTheme = Ui.Theme`. Page and navigation icons are colour SVGs in `Assets/Icons` (`Ui.Icon`, `Ui.NavIcon`, `Ui.IconFor`), shared and rasterized small; button glyphs take `Ui.GlyphColor` (plain on accent buttons).
- **WinUI:** pages are composed in code with `Pages/Ui.cs`; set `AcceptsReturn` before `Text` on multi-line boxes. Glyph constants use `\uXXXX` escapes. A page that switches the app's session rebuilds itself; long work (scans) uses its own `HubwrightSession`. Long work runs from the async `Ui.Button` (spinner on the button, the action named in the strip above the page) or inside `Activity.Begin`; progress lines go through `Activity.Report`. `Ui.Row` wraps; don't use a horizontal StackPanel for rows that can outgrow their column.
- **No shell screenshots.** Verify UI by building, running and asking the user to look.
